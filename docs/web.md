# Frontend — apps/web

Vite 8 + React 19 SPA (port 5173). TanStack Router (file-based), TanStack Query
for data fetching, React Hook Form + Zod resolvers, Tailwind CSS v4, Base UI
components. API base URL is configured through VITE_API_URL.

## Structure

```
src/
  main.tsx                      Entry — theme, QueryClientProvider, RouterProvider
  router.tsx                    TanStack Router instance (routeTree.gen.ts)
  routeTree.gen.ts              Auto-generated by the TanStack Router plugin — do not edit
  routes/                       File-based routing
    __root.tsx                  Root layout (Outlet)
    <path>.tsx                  One file per URL path
  features/<feature>/           One folder per feature (see below)
  components/ui/                Base UI primitives (button, input, card, alert, label)
  lib/                          Shared client helpers (api-client, query-client, theme, utils)
  config/                       App-level config (env)
  global.css                    Tailwind v4 entry + oklch CSS variables
```

## Folder roles — where to put what

| Folder          | Purpose                                                            | Used for |
| --------------- | ------------------------------------------------------------------ | -------- |
| `routes/`       | File-based route definitions — one file per URL path.               | `__root.tsx` (layout + `Outlet`) and one `*.tsx` per path. Pages stay thin and compose feature components. |
| `features/<feature>/` | **Feature-specific code.**              | `api.ts`, `queries.ts`, presentational components. |
| `components/ui/` | Reusable Base UI primitives (button, input, card, alert, label).    | Generic, non-feature components. Keep feature-specific UI inside `features/<feature>/`. |
| `lib/`          | Shared client infrastructure used across features.                  | `api-client.ts`, `query-client.ts`, `theme.ts`, `utils.ts` (`cn`). Add here only if reused widely. |
| `config/`       | App-level configuration.                                            | `env` (VITE_API_URL). |

Rule of thumb: **new feature code → `features/<feature>/`**. Reusable generic
components → `components/ui/`. Only add to `lib/` when something is genuinely
shared across features. Routes are thin — they import feature components, they
don't contain logic.

## Routing

- File-based routing via `@tanstack/router-plugin` (auto code splitting on).
  Route files are generated into `routeTree.gen.ts` — never edit it by hand.
- Route files export `Route` via `createFileRoute('/path')` and compose feature
  components.
- Root layout wraps everything with `Outlet` in `__root.tsx`.

## Feature organization

Each feature lives under `src/features/<feature>/` and is composed of:

| File           | Responsibility                                                        |
| -------------- | --------------------------------------------------------------------- |
| `api.ts`       | Thin wrappers around `apiClient` (typed requests, one fn per endpoint) |
| `queries.ts`   | Query keys + React Query hooks (useQuery/useMutation)                   |
| `*.tsx`        | Feature components (pages, lists, cards, forms, and other feature-specific UI)                            |

**`api.ts`** — uses `apiClient` from `@/lib/api-client.js`. List endpoints return
`{ data, meta }` via `getPaginated`; single resources via `get`/`post`/`patch`/`delete`.

**`queries.ts`** — the key factory pattern:
```ts
export const featureKeys = {
  all: ['features'] as const,
  lists: () => [...featureKeys.all, 'list'] as const,
  list: (params) => [...featureKeys.lists(), params] as const,
  details: () => [...featureKeys.all, 'detail'] as const,
  detail: (id) => [...featureKeys.details(), id] as const,
};
```
Mutations invalidate the relevant keys (`onSuccess`) so lists stay fresh.
Forms use React Hook Form + `zodResolver` with schemas from `@repo/shared-schemas`.

## Data fetching

- React Query (`@tanstack/react-query`) is the only server-state layer; no
  global client state library (zustand/redux) is used.
- Query keys are feature-scoped and invalidated on mutation success — see the
  `featureKeys` pattern under Feature organization.
- Loading/error/empty states are handled inline in components, using
  `<Alert variant="destructive">` for errors.

## Styling

Follow the design system: semantic tokens, `components/ui/` primitives, theme,
layout, typography, and forms — see `docs/design.md`.

## Adding a new feature / page

A ready-to-copy template lives in `apps/web/templates/feature/` (`api.ts`,
`queries.ts`). Copy it to `src/features/<feature>/`, rename
`feature` → `<feature>` and `Feature` → `<Feature>` (names, imports, query keys,
API paths), then edit.

1. Copy `apps/web/templates/feature/` → `src/features/<feature>/` and rename as
   above.
2. Add the domain types/schemas to `@repo/shared-schemas` / `@repo/shared-types`
   (or reuse existing ones) so `api.ts` imports resolve — see
   `docs/shared-packages.md`.
3. Create a route file under `src/routes/<path>.tsx` exporting a
   `createFileRoute(...)` component that imports the feature components.
   The route tree regenerates automatically via the dev server / router plugin.
4. Verify: `pnpm --filter web typecheck`, `pnpm lint`.

The `apps/web/templates/feature/` folder is the canonical source for new
feature structure. Existing features may contain feature-specific differences
and should not be treated as templates.

## Notes / conventions

- Web uses Bundler module resolution, so import extensions are optional. Follow
the existing import style of the file being edited. Path alias: @/ → src/.
- `no-console` is a warning for web — avoid `console.log` in components.
- Web has no tests — see `docs/development.md` → Test structure.
